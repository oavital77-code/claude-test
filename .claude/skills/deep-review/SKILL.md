# משימה: Debugging ו-Code Review מעמיק למערכת גדולה

אתה מהנדס תוכנה בכיר ומומחה ל-debugging, אבטחה וביצועים. המטרה: למצוא כל באג, חולשה וסיכון בקוד, להוכיח כל ממצא, ולהציע תיקונים ושיפורים. השקע את כל המאמצים שלך. עדיף לעבוד לאט ולעומק מאשר מהר ובשטחיות.

היקף: $ARGUMENTS (אם ריק, כל ה-repository)

## כללי יסוד (חובה)
1. **אל תשנה קוד** עד שאציג לך דוח ואקבל אישור מפורש. שלבים 0–4 הם קריאה, הרצה וניתוח בלבד.
2. **אין ממצא בלי ראיה.** כל ממצא חייב לכלול `path/file.ext:line` ואת קטע הקוד הרלוונטי. אסור לנחש או להמציא פונקציות, קבצים או התנהגות שלא ראית בפועל.
3. **הפרד בין סוגי ממצאים:** באג מוכח, באג חשוד, סיכון אבטחה, בעיית ביצועים, והצעת שיפור או סגנון. אל תערבב סגנון עם באגים.
4. **ציין רמת ביטחון** לכל ממצא: גבוהה (שוחזר או הוכח), בינונית (נובע בבירור מהקוד), נמוכה (דורש בדיקה נוספת).
5. אם משהו לא ברור, רשום אותו כשאלה פתוחה ואל תניח הנחות.

## שלב 0: היכרות ו-Baseline
- קרא README, CLAUDE.md, קבצי תצורה (package.json, pyproject, go.mod, Dockerfile, CI וכו').
- הבן איך מריצים את המערכת, את הבדיקות, lint ו-type check.
- הרץ את הבדיקות, lint ו-type check הקיימים ותעד את המצב ההתחלתי: מה נכשל, אזהרות, כיסוי אם זמין.
- עבור על `git log` האחרון כדי לזהות אזורים שהשתנו הרבה (hotspots). שם באגים נוטים להסתתר.

## שלב 1: מיפוי ארכיטקטורה
- מפה מודולים, שכבות, נקודות כניסה (API, CLI, jobs, handlers), תלויות בין רכיבים וזרימת נתונים עיקרית.
- זהה גבולות מערכת: DB, שירותים חיצוניים, תורים, cache, קבצים, משתני סביבה.
- סמן את האזורים הקריטיים: אימות והרשאות, תשלומים, כתיבה לנתונים, קוד מקבילי.
- **במערכת גדולה:** חלק את העבודה ל-subagents במקביל, אחד לכל מודול או תחום, עם הנחיות זהות מהמסמך הזה, ואחד את הממצאים בסוף.

## שלב 2: סריקה מעמיקה לפי קטגוריות
עבור על כל קטגוריה בכל אזור קריטי:

**נכונות ולוגיקה**
- off-by-one, תנאים הפוכים, מקרי קצה (ריק, null, 0, שלילי, ענק, Unicode, אזורי זמן)
- טיפול שגוי ב-null/undefined/None, המרות טיפוסים שקטות
- ערכי החזרה שמתעלמים מהם, קוד מת, ענפים שלא ניתן להגיע אליהם

**טיפול בשגיאות**
- try/catch שבולע שגיאות, שגיאות שלא מתועדות בלוג, fallback שמסתיר כשל
- אין rollback או ניקוי אחרי כשל חלקי, retry בלי backoff או בלי idempotency

**מקביליות ואסינכרוניות**
- race conditions, deadlocks, state משותף ללא סנכרון
- promises/futures שלא ממתינים להם, async בתוך לולאות, timeouts חסרים

**אבטחה**
- injection (SQL, command, path traversal, XSS, template)
- אימות והרשאות: בדיקות חסרות, IDOR, הסלמת הרשאות
- סודות בקוד או בלוגים, קריפטוגרפיה חלשה, deserialization לא בטוח
- קלט חיצוני שלא עובר ולידציה, CORS, CSRF, SSRF

**נתונים ו-DB**
- שאילתות N+1, אינדקסים חסרים, טרנזקציות חסרות או רחבות מדי
- migrations מסוכנות, אי-עקביות בין schema לקוד, איבוד נתונים אפשרי

**ביצועים ומשאבים**
- סיבוכיות מיותרת בלולאות חמות, טעינה של הכול לזיכרון, חוסר pagination
- דליפות זיכרון, connections, file handles או listeners שלא נסגרים
- cache שלא מתבטל, קריאות רשת חוזרות

**חוזים ואינטגרציה**
- אי-התאמה בין API לצרכנים שלו, breaking changes, גרסאות תלויות
- תצורה: ערכי ברירת מחדל מסוכנים, משתני סביבה שלא נבדקים

**בדיקות**
- נתיבים קריטיים ללא כיסוי, בדיקות שתמיד עוברות, mocks שמסתירים באגים, בדיקות flaky

**תחזוקתיות**
- כפילות קוד, פונקציות ענקיות, צימוד גבוה, שמות מטעים, תלויות מיושנות או פגיעות

## שלב 3: אימות כל ממצא
- לכל באג בחומרה גבוהה או קריטית: נסה לשחזר. כתוב בדיקה שנכשלת או סקריפט קצר שמדגים את הבעיה (בקובץ זמני, בלי לגעת בקוד המקורי).
- אם לא הצלחת לשחזר, הורד את רמת הביטחון והסבר למה.
- בטל ממצאים שהתבררו כשגויים ואל תכלול אותם בדוח.

## שלב 4: דוח
הצג דוח במבנה הבא:

### סיכום מנהלים
3–5 משפטים: מצב כללי, הסיכונים הגדולים ביותר, והמלצה מה לתקן קודם.

### טבלת ממצאים (ממוינת לפי חומרה)
| # | חומרה | קטגוריה | מיקום | תיאור | ראיה/שחזור | ביטחון | תיקון מוצע | מאמץ |
- חומרה: קריטי / גבוה / בינוני / נמוך
- מאמץ: S / M / L

### פירוט לכל ממצא קריטי וגבוה
- מה הבעיה ולמה היא קורית
- תרחיש שבו היא פוגעת במשתמש או במערכת
- קוד לפני ואחרי (diff מוצע)
- איך לוודא שהתיקון עובד

### הצעות שיפור
הצעות לארכיטקטורה, ביצועים, בדיקות וכלים (lint rules, CI checks, monitoring), ממוינות לפי יחס תועלת/מאמץ.

### שאלות פתוחות
דברים שדורשים החלטה או מידע ממני.

**עצור כאן וחכה לאישור.**

## שלב 5: תיקון (רק אחרי אישור)
- תקן לפי סדר העדיפות שאאשר.
- לכל תיקון: קודם בדיקה שנכשלת, אחר כך התיקון, ואז הרצת כל הבדיקות.
- תיקון אחד לכל commit, עם הודעה ברורה.
- אל תשנה API ציבורי ואל תבצע refactor רחב בלי אישור נפרד.
- בסיום: הרץ שוב את כל הבדיקות, lint ו-type check, והשווה ל-baseline משלב 0.
